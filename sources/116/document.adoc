.Foreword
This document is part of the Metanorma specifications series. It defines the
machine serialization format for Metanorma documents, developed in response to
the need for AI- and retrieval-ready document output
(https://github.com/metanorma/metanorma/issues/592[mn-for-ai issue #592]).

== Introduction

Metanorma compiles semantic authoring sources into presentation formats
(HTML, PDF, DOCX) intended for human readers. Machine consumers — retrieval
pipelines, question answering over standards, conformity-assessment tooling,
training-corpus curation — currently re-derive document semantics by scraping
the compiled HTML: clause numbers are recovered from heading text, tables are
flattened into prose, equations are skipped, and document status is joined
from external bibliographic databases. Every one of those workarounds exists
because the renderer holds the semantics in memory while building the output
but does not emit them.

This specification defines *Metanorma Knowledge Objects (MKO)*: a derived,
deterministic, machine serialization of a Metanorma document as a bundle of
typed, addressable knowledge objects. The format is a *projection* over the
typed document model — exactly like a rendering, it is derived output that is
lossy by design and never a source format. The semantic model and semantic XML
remain canonical.

The design goal is *addressability*: stable unit identifiers, declared unit
types, clean text, typed payloads, and a flat edge list exposing containment
and semantic relations. Chunking policy, embedding, and all model-layer
choices remain with consumers; MKO emits semantic units, not chunks.

=== Design principles

* *Derived output.* An MKO bundle is generated from the document model. It is
  never authoritative; regeneration replaces it wholesale.
* *Deterministic.* Given the same source model and the same schema version,
  a producer emits byte-identical components.
* *Flavor-agnostic.* One format serves every Metanorma flavor. The
  projection walks typed model classes and declared attributes only; it has
  no per-flavor code paths.
* *Encoding-split schema.* The schema is one typed object model with JSON
  serialization; consumers may treat components as JSON documents.
* *Self-contained identity.* Document identifiers, status, relations, and
  parsed publication identifiers travel inside the bundle — no external
  bibliographic join is required to establish what the document is.

== Scope

This specification defines:

* the MKO bundle structure and its components (<<section:bundle>>);
* the manifest and integrity model (<<section:manifest>>);
* the document identity component (<<section:identity>>);
* the typed unit model and typed payloads
  (<<section:units>>, <<section:payloads>>);
* the edge model (<<section:edges>>);
* the auxiliary components for bibliographic data, identifiers, and
  glossaries (<<section:auxiliary>>);
* producer conformance requirements and consumer expectations
  (<<section:conformance>>);
* stability and versioning rules (<<section:stability>>).

This specification does not define chunking policy, embeddings, model
output, or any consumer-side processing of MKO bundles.

== Terminology

bundle:: the directory (or ZIP archive of one) containing all MKO components
for exactly one document.

unit:: one addressable semantic object extracted from the document model
(a clause, term, table, formula, figure, note, example, source code block,
requirement, or reference entry).

anchor:: the identifier the document model carries for an element, when
present.

breadcrumb:: the ordered sequence of ancestor section titles for a unit.

projection:: the deterministic walk that derives units and edges from the
document model.

payload:: the typed, unit-specific data structure carried by a unit in
addition to its common fields.

edge:: a directed relation between two units, or between a unit and an
external key.

== Bundle structure ==

An MKO bundle for a document with short identifier `iso-17301-1-2016` is a
directory named `<short>.mko` (or the ZIP archive `<short>.mko.zip` with
identical contents):

....
iso-17301-1-2016.mko/
  manifest.json        # bundle manifest and integrity hashes
  document.json        # document identity, status, structure tree
  units.jsonl          # typed units, one JSON object per line
  edges.jsonl          # edges, one JSON object per line
  bibdata.json         # Relaton bibliographic record
  identifiers.json     # parsed publication identifiers
  glossary.json        # per-document term glossary
....

`manifest.json`, `document.json`, `bibdata.json`, `identifiers.json`, and
`glossary.json` are JSON objects. `units.jsonl` and `edges.jsonl` are
line-oriented JSON: each line is exactly one JSON object, keys sorted
canonically, no blank lines. Line-oriented encoding keeps the two unbounded
components streamable and diff-friendly.

[[section:manifest]]
== Manifest

`manifest.json` is the bundle's entry point.

[source,json]
----
{
  "schema": "metanorma-mko",
  "schema_version": "1.0.0",
  "generated": {
    "tool": "metanorma-document",
    "schema_version": "1.0.0",
    "flavor": "iso",
    "timestamp": "2026-08-28T00:00:00Z"
  },
  "source": "document-en.xml",
  "source-hash": "sha256:…",
  "components": [
    { "name": "document", "file": "document.json",
      "media_type": "application/json", "count": 1, "hash": "sha256:…" },
    { "name": "units", "file": "units.jsonl",
      "media_type": "application/jsonl", "count": 142, "hash": "sha256:…" }
  ],
  "license": "…",
  "copyright": "…"
}
----

Each `components` entry carries the component name, file name, media type,
object count (for line-oriented components, the line count; `1` for single
JSON objects), and the SHA-256 hash of the file's bytes.

[[section:identity]]
== Document identity

`document.json` carries what the document *is*, without external joins.

[source,json]
----
{
  "ids": {
    "canonical": "ISO 17301-1:2016",
    "short": "iso-17301-1-2016",
    "docid": ["ISO 17301-1:2016", "ISO 17301-1:2016(E)"],
    "urn": ["urn:iso:std:iso:17301:-1:ed-2:v1:en"]
  },
  "flavor": "iso",
  "doctype": "international-standard",
  "titles": [{ "lang": "en", "text": "Cereals and pulses …" }],
  "edition": "2",
  "languages": ["en"],
  "status": { "stage": "60", "substage": "60", "abbreviation": "published" },
  "dates": [{ "type": "published", "on": "2016-05-01" }],
  "relations": [{ "type": "obsoletes", "to": "ISO 17301-1:2009" }],
  "structure": [
    { "id": "u:_1b587120…", "number": "3", "title": "Terms and definitions",
      "children": [ /* nested StructureNode */ ] }
  ]
}
----

`ids.canonical` is the primary, non-URN document identifier as authored;
`ids.short` is a slug derived from it and names the bundle. `structure` is
the section containment tree with numbering as presented; its node `id`s
reference the corresponding `clause` units.

[[section:units]]
== Units

Each line of `units.jsonl` is one unit. Common fields:

[source,json]
----
{
  "id": "u:97f3c1d2ab04e5f6",
  "type": "table",
  "anchor": "table-3",
  "number": "3",
  "title": "Maximum permissible errors",
  "parent": "u:1a2b3c4d5e6f7a8b",
  "breadcrumb": ["4 Metrological requirements", "4.1 Classification"],
  "obligation": "normative",
  "lang": "en",
  "text": "… human-readable display text …",
  "payload": { /* typed, see Clause 7 */ },
  "hash": "sha256:…"
}
----

* `id` — the stable unit identifier: `u:` + 16 hex characters derived from
  the content hash (see <<section:stability>>).
* `type` — one of the unit types in <<table:unit-types>>.
* `parent` — the `id` of the containing unit, absent for top-level units.
* `text` — plain display text extracted from the model (never scraped from
  rendered HTML).
* `payload` — the typed payload for the unit's type; present when the type
  defines one.

[[table:unit-types]]
.Unit types
|===
| Type | Source | Payload

| `clause` | a section (including preface sections and annexes, which carry their own type) | —
| `annex` | an annex section | —
| `term` | a term entry | TermPayload
| `table` | a table | TablePayload
| `figure` | a figure | FigurePayload
| `formula` | a formula / stem block | FormulaPayload
| `note` | a note | —
| `example` | an example | —
| `sourcecode` | a source code block | —
| `requirement` | a requirement, permission, or recommendation (obligation distinguishes them) | RequirementPayload
| `reference` | a bibliographic entry | ReferencePayload
|===

[[section:payloads]]
== Typed payloads

.TablePayload
[source,json]
----
{
  "caption": "Maximum permissible errors",
  "columns": [{ "label": "Load m", "unit": "e" }],
  "rows": ["0 ≤ m ≤ 5·10³ | 0.5e"],
  "embed_text": "Table: Maximum permissible errors; columns: …; row: …"
}
----

Tables are emitted as structure, never only as linearized text: `columns`
carries labels and units when the model declares them, `rows` carries one
entry per table row with cell values joined by ` | `. `embed_text` is a
deterministic convenience serialization for embedding; consumers may ignore
it and serialize their own.

.FormulaPayload
[source,json]
----
{ "asciimath": "n_LC <= 10^4", "mathml": "…", "description": "…" }
----

At least two of `asciimath`, `mathml`, `description` SHOULD be present, so
that retrieval can index a textual form while renderers retain the
mathematical form.

.TermPayload
[source,json]
----
{
  "concept": "paddy",
  "designations": ["paddy"],
  "definition": "rice retaining its husk after threshing",
  "sources": [{ "citeas": "ISO 7301:2011" }]
}
----

.RequirementPayload
[source,json]
----
{
  "identifier": "/req/iso-17301/classification/nlc-limit",
  "class": "/req/iso-17301/classification",
  "obligation": "requirement",
  "subject": "load cell",
  "statement": "The number of verification intervals shall …",
  "inherits": []
}
----

.FigurePayload
[source,json]
----
{ "alt": "…", "uri": "…", "caption": "…" }
----

.ReferencePayload
[source,json]
----
{ "key": "ISO7301", "cited": "ISO 7301:2011" }
----

[[section:edges]]
== Edges

Each line of `edges.jsonl` is one directed edge:

[source,json]
----
{ "from": "u:…", "to": "u:…", "kind": "part_of" }
----

.Edge kinds
|===
| Kind | From → To | Meaning

| `part_of` | unit → unit | containment; mirrors `parent` on units
| `cites` | reference unit → `ext:<citeas>` | citation to another document
| `defines` | term unit → `concept:<anchor>` | term defines a concept
| `class_of` | requirement unit → `class:<klass>` | membership in a requirements class
|===

`to` values that are not unit ids are prefixed external keys (`ext:`,
`concept:`, `class:`). Consumers resolve them against `bibdata.json`,
`glossary.json`, or their own concept registries.

[[section:auxiliary]]
== Auxiliary components

The auxiliary components carry the *native object-model serializations* of
the Metanorma ecosystem, decomposed at the document-model layer
(`Metanorma::Document::NativeModels`) — never re-flattened into a parallel
schema:

* `bibdata.json` is the bibliographic record as native Relaton JSON (the
  relaton monogem's own wire shape, including its `schema_version`).
* `identifiers.json` carries each document identifier with the pubid
  monogem's native parse when a pubid flavor covers it:

[source,json]
----
{ "identifiers": [
    { "original": "ISO 17301-1:2016", "type": "ISO", "primary": true,
      "parsed": { "_type": "pubid:iso:international-standard",
                  "number": "17301", "part": "1", "year": "2016" } }
] }
----

* `glossary.json` is the per-document glossary as native Glossarist
  concepts — `Glossarist::Concept` objects serialized by the glossarist
  gem's own framework:

[source,json]
----
{ "concepts": [
    { "data": { "id": "term-paddy-eng", "language_code": "eng",
        "terms": [{ "type": "expression", "normative_status": "preferred",
                    "designation": "paddy" }],
        "definition": [{ "content": "rice retaining its husk after threshing" }],
        "sources": [{ "type": "authoritative",
                      "origin": { "ref": { "source": "ISO 7301:2011" } } }],
        "entry_status": "valid" } }
] }
----

[[section:conformance]]
== Conformance

=== Producers

An MKO producer SHALL:

. emit `manifest.json` with `schema: "metanorma-mko"`, the schema version,
  and per-component byte hashes that verify;
. emit the document identity component with `ids.canonical` populated from
  the authored document identifier (never slug-derived);
. assign every unit an `id` and a `type` from <<table:unit-types>>;
. keep unit `id`s stable across regenerations for unchanged content
  (content-hash basis);
. emit tables as columns and rows, never as linearized strings only;
. emit edges only referencing present unit ids or declared external keys;
. carry `license` and `copyright` in the manifest when the source declares
  them.

=== Consumers

An MKO consumer SHOULD treat unit types it does not recognize as opaque
text nodes (forward compatibility), and SHOULD verify component hashes
against the manifest before relying on bundle contents.

[[section:stability]]
== Stability and versioning

Unit `id`s are `u:` followed by the first 16 hex characters of the SHA-256
content hash of the unit's stable fields. Unchanged content therefore
re-derives the same `id`, enabling incremental re-indexing across document
revisions; any content change yields a new `id` for the affected unit only.

The schema version follows semver. Additive changes (new unit types, new
payload fields, new edge kinds) increment the minor version; changes that
alter the meaning of existing fields increment the major version. The
`schema` identifier `metanorma-mko` is constant.

Determinism is normative: given the same source model and schema version,
repeated exports are byte-identical (timestamps in `manifest.json` excepted).

== Relationship to other Metanorma outputs

MKO is a sibling of the HTML/PDF/DOCX renderings, produced from the same
typed document model through the same format registry. It is derived and
lossy: the semantic XML remains the canonical interchange between Metanorma
toolchain stages, and an MKO bundle is never a compilation source. Where the
presentation model provides numbering, MKO carries the presented numbers;
MKO does not recompute presentation.

== API and CLI

The reference implementation lives in the `metanorma-document` gem:

[source,ruby]
----
Metanorma::Mko.export(xml_or_model, to: dir, presentation_xml: nil, zip: false)
Metanorma::Mko.generate(document, **options) # registry path (compile pipeline)
----

The CLI format name is `mko`:
`metanorma compile document.adoc -x mko` writes `<short>.mko/` (or
`<short>.mko.zip` with the archive option) next to the other outputs.
